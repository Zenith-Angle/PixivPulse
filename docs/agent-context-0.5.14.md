# Agent 0.5.14：取消预算，减少重复数据

> 历史记录：0.5.15 已取消本文的逐工具自动小结，改为按问题取数和服务式反馈，当前行为见 [0.5.15 改造说明](./agent-workflow-0.5.15.md)。

## 根因与修改边界

旧 runner 把 JSON 的 UTF-8 字节量当作保守 token 估算，并同时执行单次、累计、输出预留、历史选择及工具结果容量检查。长问题可能尚未发给模型就被拒绝；累计估算还会提前关闭工具。正文批量读取共享结果额度，已读工作集达到阈值后也会拒绝继续读取。

Responses 与 Chat Completions 的回归均先复现了“当前问题超出上下文预算”。本次删除这些预算字段、校验、工具关闭条件、结果裁剪和历史裁剪，也不再向服务发送 `max_output_tokens`、`max_completion_tokens` 或 `max_tokens`。删除输入框的 30,000 字符限制和回答／推理流的本地累计长度拦截。

读取旧配置时只恢复当前字段，保存时丢弃旧预算；API 地址、密钥存储方式、模型、数据授权和阅读偏好不变。工具轮数、用户停止、无响应超时、网站访问与冷却仍各自按原有职责工作。

## 怎样减少上下文

1. **先计算，再传输。** 本地排行、分组、比较及增长工具直接处理全库；按问题选取结果，避免全量历史进入模型。
2. **无损编码。** 同结构多行对象可表示为 `{$table:{columns,rows}}`，只发送一次列名。只有更小时才启用；数字、null、限制说明、分页和行顺序完整保留。原始 JSON 单独保存在来源和导出中。
3. **稳定引用。** 递归规范化工具参数；重复查询总是引用最初的来源，不重复发送大结果、不产生引用链。首次概览也参与复用。数组顺序仍有意义，不排序。
4. **渐进正文。** 自动档每次每篇约 3,000 个 Unicode 字符，按未读位置继续，更多作品不会挤占其他篇的采样量。网站请求仍逐一执行；来源位置及内容指纹检查保留。
5. **笔记与工作集分离。** `record_reading_notes` 可整理正文或统计。模型需要保留来源、关键数字、观察、假设、缺口和下一步；确认笔记参数有效后，后续工作上下文里的原始结果换成来源笔记。笔记只出现一次，工具参数和返回值不重复回显。
6. **原始证据可回查。** `retrieve_evidence` 按 Unicode 字符位置分页返回本问原始来源，包括已整理的正文。精确引用时可重新读取，不必重访 Pixiv。原始来源不因工作集整理而删除。

工作集增大时提示模型及时整理，但没有强制额度、拒绝读取或静默截断。笔记整理仍依赖模型调用工具；其内容是模型解释，不是新事实。当前问题与已完成历史回答完整保留，不能保证任意长的对话永远适合某个模型。

## 流式反馈与会话

- 发送后立即显示启动状态；模型轮次显示当前步骤，已识别的工具在参数接收阶段就显示可读动作名称。
- 每次实际工具执行结束，都生成一句基于返回结果的阶段小结；模型被要求在重要发现处进一步说明成果与下一步。模型的私有推理不展示。
- 公开进展、执行详情与最终答案分开。连续两次进展说明不会被误判为重复数据查询、导致工具提前关闭。
- UI 合并高频刷新，每次刷新只复制可变容器，复用原始来源字符串，避免随着长对话增长不断深拷贝所有证据。
- 超时改为无响应计时：每次收到流式事件重置；持续有输出的长请求不会因为应用总时长被停止。断流、失败、用户停止仍明确显示。
- 初次进入、切回和刷新默认新对话，并回到欢迎内容顶部；历史需主动选择。切换页面不会取消后台任务，完成后也不会抢回新对话选择。

## 验证与可观察边界

- 两种 SDK 协议：长问题完整发送，旧预算不起作用，请求中没有输出上限字段；大结果完整返回。
- 固定的 100 行统计夹具：UTF-8 序列化体积减少超过 30%，解码后与原始对象完全相同。
- 两种协议的 30 行大结果链路：查询 → 笔记 → 重复引用 → 原始来源回查 → 回答。整理后工作上下文长度少于整理前一半，笔记只出现一次，原始 30 行仍完整可查。
- 流式回归：10 秒无响应超时下，持续收到事件的请求运行 36 秒仍正常完成；真正停滞的流仍超时。
- 浏览器：生产 bundle + 本机确定性 SSE 服务，验证部分答案在结束前可见、阶段小结、切回新对话、后台完成、历史继续、刷新默认空白和请求不携带输出上限；浏览器控制台无错误或警告。
- 完整 69 个测试文件、512 项测试通过；类型检查、生产 ZIP 和本地扩展构建校验通过。

以上体积变化不是实际 token 账单比例，夹具也不代表真实模型的分析质量。本次未使用私人 API key 重跑线上长分析。服务商仍可能受实际上下文容量、默认生成上限、账户额度或服务状态约束；应用不会绕过这些限制。
